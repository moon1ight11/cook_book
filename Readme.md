## Возможности
- **Веб-клиент** — Next.js: каталог рецептов с фильтрами и пагинацией, поиск по тегам, страницы рецепта, создания и редактирования, «Мои рецепты», профиль, страница рецептов автора и админ-панель
- **Аутентификация** — JWT-токены: access-токен в HttpOnly cookie, refresh-токен в теле ответа
- **Управление пользователями** — регистрация, вход, обновление профиля, удаление аккаунта
- **Управление рецептами** — CRUD операции, поиск по тегам, фильтрация по названию и сложности
- **Ролевая модель** — разделение на обычных пользователей (`Basic`) и администраторов (`Admin`)
- **Пагинация** — постраничный вывод списка рецептов с настраиваемым размером страницы (1–100, по умолчанию 10)
- **Кэширование** — самодельный in-memory кэш с TTL для хранения рецептов и результатов поиска по тегам
- **Мониторинг** — экспорт метрик в Prometheus и визуализация в Grafana
- **Логирование** — структурированное логирование с ротацией файлов
- **Контейнеризация** — Docker и Docker Compose для локальной инфраструктуры
- **CI/CD** — автоматическая сборка и публикация образа API в GitHub Container Registry

## Архитектура
Бэкенд построен на принципах **Clean Architecture** с четким разделением на слои:
- **Handler / Delivery** — HTTP-обработчики (Echo).
- **Service / Usecase** — бизнес-логика приложения.
- **Repository** — слой доступа к данным (MongoDB).
- **Domain** — модели, не зависящие от внешних фреймворков.

Фронтенд — приложение Next.js с App Router и разделением по фичам:
- **`app/`** — страницы и маршруты: каталог, поиск, рецепты, профиль, админка.
- **`components/`** — переиспользуемые UI-компоненты и layout.
- **`features/`** — API-клиенты, хуки и формы по доменным областям (`auth`, `recipes`, `profile`, `admin`).
- **`lib/`** — axios-клиент с refresh-интерцептором, Zustand-store, утилиты.
- **`types/`** — TypeScript-типы API.


## Быстрый старт
### Предварительные требования
- Docker и Docker Compose
- *(Опционально, для запуска без контейнеров)* Go 1.25+, Node.js 20.9+ и MongoDB 7.0

### Запуск в Docker (рекомендуемый способ)
1. **Клонировать репозиторий**
2. **Создать файл переменных окружения**
   Скопируйте `.env.example` в `.env` и заполните секреты и пароли:
```bash
   cp .env.example .env
```
3. **Собрать и запустить все сервисы**
```bash
   docker compose up -d --build
```
   *(Чтобы дополнительно запустить веб-интерфейс Mongo Express, добавьте профиль: `docker compose --profile tools up -d --build`)*

4. **Проверить работоспособность**
```bash
   curl http://localhost:8080/health
   # Ответ: OK
```
   - Веб-клиент (Next.js): http://localhost:3000
   - REST API (Go): http://localhost:8080
   - Grafana: http://localhost:3002 (привязана к `127.0.0.1`)
   - Prometheus: http://localhost:9090 (привязан к `127.0.0.1`)

### Локальный запуск для разработки (без Docker для приложения)
1. Скопируйте `config.example.yaml` в `config.yaml` (параметры из файла можно переопределять через переменные окружения с префиксом `COOKBOOK_`, например `COOKBOOK_SERVER_PORT`).
2. Поднимите инфраструктуру: `docker compose up -d mongodb prometheus grafana`
3. Запустите бэкенд: `go run cmd/main.go`
4. Запустите фронтенд: `cd frontend && npm install && npm run dev`

## API Документация
Подробное описание всех эндпоинтов с примерами запросов и ответов доступно в файле [OpenAPI.yaml](./docs/OpenAPI.yaml).
Для удобства можно импортировать спецификацию в Postman, Insomnia или Swagger UI (базовый URL — `http://localhost:8080/api`).

Основные группы эндпоинтов:

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| POST | `/api/v1/auth/sign-up` | публичный | Регистрация и автоматический вход |
| POST | `/api/v1/auth/sign-in` | публичный | Вход |
| POST | `/api/v1/auth/token-refresh` | публичный | Обновление пары токенов по refresh-токену |
| POST | `/api/v1/private/sign-out` | Basic, Admin | Выход и отзыв refresh-токена |
| GET | `/api/v1/public/recipes` | публичный | Список рецептов (`page`, `page_size`, `title`, `difficulty`) |
| GET | `/api/v1/public/recipes/{recipe_id}` | публичный | Детальная информация о рецепте |
| GET | `/api/v1/public/recipes-by-tags` | публичный | Поиск по тегам (`tags` можно передавать несколько раз) |
| GET | `/api/v1/public/recipes-by-user/{user_id}` | публичный | Рецепты пользователя |
| POST | `/api/v1/private/recipes` | Basic, Admin | Создание рецепта |
| PATCH | `/api/v1/private/recipes/{recipe_id}` | Basic, Admin | Обновление своего рецепта |
| DELETE | `/api/v1/private/recipes/{recipe_id}` | Basic, Admin | Удаление своего рецепта |
| GET | `/api/v1/private/users` | Basic, Admin | Текущий пользователь |
| PATCH | `/api/v1/private/users` | Basic, Admin | Обновление своего профиля |
| DELETE | `/api/v1/private/users` | Basic, Admin | Удаление своего аккаунта |
| POST | `/api/v1/admin/users` | Admin | Создание администратора |
| PATCH | `/api/v1/admin/users/{user_id}` | Admin | Изменение роли пользователя |
| DELETE | `/api/v1/admin/users/{user_id}` | Admin | Удаление любого пользователя |
| DELETE | `/api/v1/admin/recipe/{recipe_id}` | Admin | Удаление любого рецепта |

Служебные эндпоинты: `GET /health` — проверка живости, `GET /metrics` — метрики Prometheus.

Аутентификация работает через cookie, поэтому браузерные клиенты должны отправлять запросы с `credentials: include`. CORS разрешает источник `http://localhost:3000`.


## Особенности реализации
### Кэширование
Реализован самодельный in-memory кэш с фоновой очисткой:
- **Стратегия:** cache-aside (данные сначала ищутся в кэше).
- **TTL:** настраиваемое время жизни записи (по умолчанию 5 минут), интервал очистки по умолчанию 1 минута.
- **Фоновая очистка:** горутина, которая с заданным интервалом удаляет просроченные записи; останавливается при завершении приложения.
- **Кэшируются:** отдельные рецепты по ID и результаты поиска по тегам (ключ — отсортированный список нормализованных тегов).
- **Инвалидация:** при обновлении или удалении рецепта запись этого рецепта удаляется из кэша. Результаты поиска по тегам не инвалидируются точечно и живут до истечения TTL.

### Логирование
- Структурированное логирование с уровнями `DEBUG`, `INFO`, `WARN`, `ERROR` (уровень задаётся в конфиге).
- Запись логов в файл (`logs/app.log` по умолчанию) с автоматической ротацией через lumberjack (`maxsize` в мегабайтах).
- Единый формат сообщений с атрибутами `key=value` и указанием источника (`AddSource`).

### Graceful Shutdown
При получении сигнала завершения (`SIGINT`, `SIGTERM`) сервер:
1. Прекращает принимать новые соединения.
2. Ожидает завершения активных запросов (таймаут 10 секунд).
3. Корректно закрывает соединение с MongoDB.
4. Останавливает горутину очистки просроченных refresh-токенов.
5. Останавливает горутину очистки кэша.

### Очистка просроченных refresh-токенов
- Фоновая горутина запускается при старте сервера.
- Раз в 24 часа очищает в БД refresh-токены с истёкшим сроком действия.
- Graceful остановка через контекст и `sync.WaitGroup`.

### Индексы базы данных
При старте приложения автоматически создаются следующие индексы:
- **Рецепты:** `owner_id`, `tags`, `created_at` (по убыванию).
- **Пользователи:** `email` (уникальный).

### Транзакции и целостность данных
- Каждая операция записи выполняется отдельным атомарным запросом к MongoDB; многодокументные транзакции не используются.
- Обновление и удаление рецепта доступны только владельцу: в запросе к БД проверяются `_id` и `owner_id`.
- Уникальность email проверяется в сервисном слое, а в БД дополнительно действует уникальный индекс на `users.email`.
- При удалении пользователя его рецепты не удаляются каскадно и остаются в базе.

### Безопасность
- Пароли хэшируются с помощью **bcrypt** (`bcrypt.DefaultCost` = 10).
- **JWT-токены:** access-токен передаётся в HttpOnly, Secure, SameSite=Strict cookie `access_token`; refresh-токен возвращается в теле ответа и хранится на клиенте.
- Refresh-токены хранятся в БД только в виде SHA-256-хэша вместе со сроком действия.
- Активен один refresh-токен на пользователя: при входе и обновлении он ротируется, при выходе — очищается.
- Сравнение токенов через `subtle.ConstantTimeCompare` (защита от timing-атак).
- Валидация email через регулярное выражение.
- При обновлении email или пароля refresh-токен перевыпускается и клиенту не возвращается — требуется повторный вход.
- Настроены политики **CORS** для безопасного взаимодействия с фронтендом (`http://localhost:3000`).
- **Role-based middleware**: `/api/v1/private/*` доступен ролям `Basic` и `Admin`, `/api/v1/admin/*` — только `Admin`.


## Покрытие тестами
- **Модульные тесты:** сервисный слой (`user`, `recipe`), JWT-сервис, in-memory кэш.
- **Интеграционные тесты:** репозитории пользователей и рецептов.
- **Библиотеки:** testify (assert + mock), моки лежат рядом с сервисами в пакетах `mocks`.
- **Особенности:** тесты репозиториев используют реальную MongoDB на `localhost:27017` (поднимается через `docker-compose up -d`).
- **Фронтенд:** отдельного набора тестов нет; статическая проверка выполняется через `npm run lint` (ESLint).

## Мониторинг
Сервис экспортирует метрики для Prometheus (`/metrics`):
- `http_requests_total` — счетчик HTTP-запросов (labels: `method`, `endpoint`, `status`)
- `http_request_duration_seconds` — гистограмма длительности запросов (labels: `method`, `endpoint`)
- `http_requests_in_flight` — текущее количество обрабатываемых запросов
- `app_operations_total` — счетчик бизнес-операций по типу (`SignUp`, `SignIn`, `CreateRecipe`, `GetUser`, `CreateAdmin_ADMIN` и т.д.)
- `app_errors_total` — счетчик ошибок (labels: `error_type`, `handler`; типы: `bad_request_error`, `forbidden_error`, `internal_error`)
- `go_goroutines_count` — количество горутин

Готовый дашборд для Grafana: [internal/metrics/dashboard.json](./internal/metrics/dashboard.json).

Grafana доступна на http://127.0.0.1:3002, Prometheus — на http://127.0.0.1:9090 (в целях безопасности порты мониторинга и администрирования БД привязаны только к локальному интерфейсу `127.0.0.1`). Адрес API для scrape задаётся в [prometheus.yml](./prometheus.yml) (внутри Docker-сети сервис доступен как `api:8080`).


## Контейнеризация
Docker Compose поднимает весь стек приложения в единой изолированной сети:
- **API (`api`)** — Go-сервер (`golang:1.25-alpine` → `alpine`, непривилегированный пользователь), порт `8080`
- **Frontend (`frontend`)** — Next.js в режиме `standalone` (`node:22-alpine`), порт `3000`
- **MongoDB 7.0 (`mongodb`)** — основная БД с `healthcheck` и постоянным томом `mongo_data` (порт наружу не проброшен)
- **Mongo Express (`mongo-express`)** — веб-интерфейс БД с basic-auth (`127.0.0.1:8081`, запускается опционально с профилем `--profile tools`)
- **Prometheus (`prometheus`)** — сбор метрик (`127.0.0.1:9090`)
- **Grafana (`grafana`)** — визуализация метрик (`127.0.0.1:3002`)

Конфигурация всех контейнеров задаётся через файл `.env` (шаблон — [.env.example](./.env.example)). Образ API собирается из [Dockerfile](./Dockerfile), образ фронтенда — из [frontend/df/Dockerfile](./frontend/df/Dockerfile).


## CI/CD
GitHub Actions ([.github/build-and-deploy.yml](./.github/build-and-deploy.yml)) настроен на:
- Автоматическую сборку Docker-образа при ручном запуске (`workflow_dispatch`).
- Публикацию образа в **GitHub Container Registry** (`ghcr.io`) с тегом `latest`.
- Сборку из `Dockerfile` (контекст — корень репозитория).
